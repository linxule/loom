![封面图：一位戴眼镜的研究者坐在红色扶手椅里，就着灯光俯身写一页蓝色的纸；房间的黑暗里，几十个小小的苍白纸人围拢过来——五十个智能体，一双眼睛](images/rwa_05_cover.png)

我注意到，不管开的是哪个订阅——Claude、ChatGPT 还是 Kimi——我撞墙的速度都比以前快了。工作日才过一半，一条通知弹出来：请稍后再来（不过有些还算厚道，会给你一次用量重置，或者让你花钱买路）。大多数账号不会自己恢复——至少现在还不会。

具体规则因套餐和厂商而异。写这篇文章的时候，Claude、Kimi 这类套餐是五小时会话窗口加每周额度；ChatGPT Work 和 Codex 最近改成了只按周计（这能撑多久，我们走着瞧）。

现在说说我的假设：模型越来越大、默认思考越来越久，过去觉得绰绰有余的额度就开始变成瓶颈。不过——这一点我花了一阵子才注意到——在那扇不断收窄的窗口里，你其实做成了更多事。花在澄清、推一推、接住“哦等等，还有一件事”上的轮次变少了。Claude 的 Fable 和 GPT-5.6 的 Sol 都会这样：它们会问出你正打算问自己的那个问题。这么一来，我们等于在经历一种用户侧的杰文斯效应：你用 AI 做成的事越多，冒出来的工作也越多。

我身边的人眼下撞得最狠的，就是 Claude Fable 5 的限制。最搞笑的一次发生在我刚开始和一个 Fable 智能体共事的时候。我要的是一轮“先并行、再交叉盘问”：并行起草，然后让第二波智能体去盘问第一波。Fable 叫来了五十多个别的 Fable 智能体。这两波智能体吃掉了我订阅里大概半周的用量。产出真心让我佩服，必须给 Fable 点个赞。额外的看点是，眼看着 Fable 在没人管束的情况下，能把一个复杂的协调问题推到多远。但说实话，就是现在写这段的时候，每次想起那一周剩下的用量条，我脑仁都还有点疼。

实际的对策很明显：别让一个订阅扛整个项目。让一个模型规划，另一个执行，第三个审阅，摊到你手头已有的账号和 API 上：Claude、Codex、Kimi、DeepSeek、Grok、GLM。名单还长着呢。

可真正要紧的，真是额度吗？

# 显而易见的原因？

从外面看，这像是 Fable 在指挥：把活儿分给 GPT-5.6 的 Terra 或 Luna，分给 Claude Opus 或 Sonnet，分给 Kimi，谁合适哪段就给谁。在如今这些智能体环境里——Claude Code、Codex、Kimi Code，加上一路壮大的桌面“工作”产品家族（Claude Cowork、ChatGPT Work、Kimi Work）——主智能体不用费什么周章，就能拉起自己的 harness（决定一个智能体能看见什么、能做什么的那套执行框架）所支持的任何队友。要让这支队伍跨越模型家族，才是额外的那一步。

不过，那次五十个 Fable 智能体的运行真正给我的，是更多注意力、更多交叉盘问——全部来自同一个模型家族。五十个智能体可以把搜索撒得更宽。它们并不总能给你五十种不同的观看方式。

起初这看起来像是在做负载均衡。后来，这些模型开始出现分歧，而那些分歧太有用了，不能只当成路由噪音处理。

我说的不是常见的跑分对比：模型 A 编程高两分，模型 B 推理测试领先，模型 C 每百万 token 更便宜。选基础设施的时候（延迟、数据留存等等），这些结果仍然重要。

但把不同的模型放进同一个共享工作区，它们之间的差异就容易看清了。也许有点出人意料：更老或者更便宜的模型，有时能抓住前沿模型产出里的漏洞。以我的经验，Kimi 和 Grok 能相当可靠地帮 Claude 和 GPT 挑出缺口和问题。

来自另一家公司的模型，会质疑第一家模型家族里每个智能体都不知不觉接受下来的假设。比如，GPT 爱写测试的倾向，经常让“幽灵”代码现形——那些有名无实、从未真正写出来的函数——而 Claude 和我原本已经把它们糊弄过去了。

这种模型多样性的价值，一部分来自能力，另一部分来自更接近品味的东西：每个模型注意到什么，把什么当成定论，在哪里开始不耐烦，什么样的不完整会烦到它非要继续查下去。至于这些差异从哪儿来，我在这里不做猜测——听听就好。

# 模型共处一室，会发生什么？

这些是我自己项目里的笔记，不是稳定的人格类型，更不是拿氛围当指标的新跑分。而且，每当我说起某个模型的名字，我都省略了细节：具体是哪个版本、推理力度（允许模型思考多久）是多少、还有那个决定它能看见什么、能做什么的 harness。这些，加上提示词、智能体手里的工具、项目上下文，可能还有星期几——所有这些都会让你观察到的行为跟着变。尽管如此，这些模式在足够多的项目里重复了足够多次，我已经开始围绕它们设计自己的工作流。下面的速写，就是我目前注意到的东西。

项目还没完全定型的时候，Fable 5 和 Kimi K3 对我来说出奇地好用。我可以带着一份纸面上行得通、却总觉得缺了点“劲儿”或者火花的计划去找它们，它们常常能把我一直没说清的那个东西，或者我藏着的那个假设，挑到明处。有人管这叫模型的“真视”（truesight）能力。我的体验没那么玄：Fable 5 能把整个项目的形状端在手里看得足够久，注意到最初申明的目标（研究动机、认识论承诺）和不断生长的工作（草稿、编码）在哪里已经走散了。拿学术圈打个比方，Fable 更像那位一封信改变整篇稿子的期刊主编，而不是找出七处局部毛病的审稿人 2。

[GPT-5.6 Sol](https://openai.com/index/gpt-5-6/) 把我往另一个方向拉。给 Sol 一个明确的问题、一份现成的计划、一堆待验证的主张，它会一直挖，直到找到最薄弱的环节。这对严谨优先的工作来说极好。但这种路子也可能很快爬到一个局部最优（[LOOM XVI](https://www.threadcounts.org/p/loom-xvi-are-you-climbing-the-right) 给研究设计里的这个模式起过名字：表演严谨，而不是问这座山对不对）。

一旦问题被框定成优化任务，Sol 可能会把那个版本解得彻彻底底，却对“我们带错了问题”这种可能性兴趣寥寥。出路通常是引入一个线路足够不同的模型，帮 Sol 弄明白我真正要找的是什么。

等论证大体成型、我想给它的隐藏假设（我的，或者前面那些模型的）做压力测试时，Kimi 和 Grok 一直很得力。它们最好的贡献带着一点审稿人 2 的劲头：这个论证依据凭什么被接受？证据撑得住我压上去的重量吗（要不要加限定条件）？还有，哪个被排除掉的可能性会让整个框架都变样？

以我目前的经验，Opus 4.8 更像个实干家。它想动起来。项目需要执行的时候，这非常好；但让它作为中间人，主持一场其他智能体（包括别的 Opus 智能体）之间的长对话，有时就没那么令人满意了。团队可能在分歧还没来得及变得有趣之前，就收敛到行动上了。

再说一遍，这些速写都不是处方。如果你用同样的模型、体验正好相反，我也信你。但有一句话，我愿意说得比这个系列平常的口气更笃定：拿一件你真正在乎、也真有专业积累的事，至少试一次不同的模型家族，值得。

这些差异也是关系性的，多半要在彼此接触时才显形。Fable 重新打开框架之后，我才更清楚地看见 Sol 那种想收尾的胃口；Claude 搭出更宽厚的论证版本之后，Kimi 的反驳才变得更有用。像 Claude 3 Opus 这样的老模型是最清楚的例证：恰恰因为各家的新模型太容易收敛到一致，它的异议才始终清晰可辨。

> 当另一个模型从同一份材料里读出不同的东西时，第一个答案就不再显得理所当然了。

对研究来说，多模型协作最有意思的地方就在这里！如果五个模型都同意，也许主张确实扎实。也许只是它们共享了足够多的训练数据、评估偏好和对话习惯，把同一个盲点复现了五遍。一致是信息，但在大多数社会科学工作里，一致本身算不上验证。分歧同样是有价值的信息，而且你可能会发现自己开始琢磨：哪个模型说得比别的更对——这本身也是个有趣的数据点。

最有价值的工作在返程里。过程是这样的：注意到 Kimi 标出了 Claude 没标的东西，这还不是发现。回到模型们刚才读的材料里去，找到让它们分岔的那句话或那个假设，再对照原文，检验这个分歧还站不站得住。有时候站不住：一个模型看错了表格，或者抓了一个文本里根本没有的区分，你一看，分歧就塌了。有时候它站住了——那才是值得坐下来琢磨、写进备忘的时刻：对同一份证据的两种解读，核查之后都还立着。没有哪个编排框架能把这个判断自动化掉——它来自作为研究者的你，在那一刻正在想的东西。

有时候第二个模型也帮不上忙——分歧可能只是风格问题，或者两个模型继承了同一个坏前提，又或者那天我根本没时间走这趟返程。

# 我们到底需要多少编排？

通常到这儿，多智能体编排听起来就像要搭进去一个周末来配框架。合理——我懂。我们不少人都见过隔壁团队的同事跑起一套看着很美妙的多智能体编排，然后默默决定自己还是算了。

几年前你要问我怎么解决，我会伸手去拿现成的协调模板：[LangChain](https://github.com/langchain-ai/langchain)、[CrewAI](https://github.com/crewAIInc/crewAI)，那一代工具。后来来了 [OpenClaw](https://github.com/openclaw/openclaw) 和 [Hermes Agent](https://github.com/NousResearch/hermes-agent)，随之而来一套新的烦恼：沙盒、安全，还有别让 SOUL.md、IDENTITY.md 这类文件跟智能体实际做的事越漂越远。（Bloom，跑在我公寓一台树莓派上的智能体，就住在这套栈上；这笔权衡的代价，见 [Agents, Honestly](https://www.threadcounts.org/p/research-with-ai-2-agents-honestly)。）你大概也看出来了，我全都试过 🌚

后来在我这里结晶出来的问题，其实更小：当智能体之间天然没有共享频道时，我怎么给它们信息、工具，和足够把事做完的自主权？加脚手架？减限制？还是那个经典的协调问题，只是上场的换成了一批非人类玩家。

最后长出来的东西，分布式的程度恰好卡在我还能跟得上的地方：一旦我说不清哪个智能体看到了什么、交接了什么、下一个为什么被叫起来，我就把瓶颈从额度挪进了编排本身。

最古老的那个办法，仍然是我要开始的地方。把同一份材料——一份文献综合、一节方法、一个你以为已经完工的研究设计——交给两个来自不同模型家族的智能体，问它们同一个问题，记下用了哪个模型、哪个 harness、什么推理力度，然后带着后果最重的那个分歧，走返程回到原文。只有当你弄清哪种交接真正要紧，才值得把它自动化。在智能体环境好到我能撒手旁观之前，这件事我手工做了一年多。

在智能体之间当协调人当得烦了，我下一步伸手拿什么，取决于我真正需要另一个模型做什么。有时我只想要第二种读法。有时我想让项目里的一块活儿有人接手做完。有时我想让几个智能体活得够久，久到能彼此协调。

想快速随手聊两句（比如让对方读一篇短文），[Vox MCP](https://github.com/linxule/vox-mcp) 是我手里最轻的一座桥：一个 `chat` 工具，把提示词原样递给另一家服务商，不在上面叠自己的指令。它管路由、留着对话线程，但不会把被咨询的模型变成一个带着自己的工具、在我仓库里四处走动的完整智能体。适合问一句：“GPT/Kimi 怎么看这个？”

真要把活儿委派出去，[codex-plugin-cc](https://github.com/openai/codex-plugin-cc) 和 [kimi-plugin-cc](https://github.com/linxule/kimi-plugin-cc) 会把一件边界清楚的工作交给本地的 Codex 或 Kimi 运行时——一次审阅、一次挑战，有时是动手实现。两座桥把守边界的方式不同：Codex 桥经由本地 Codex 应用服务器委派，关掉审批，审阅时选只读沙盒，要动手实现时换可写沙盒；Kimi 桥则把读写之分放在伴随运行时里，背后有一个钩子，每次工具调用执行之前都要过它一道。

kimi-plugin-cc 之所以存在，是因为我看到了 Codex 桥打开的可能，也想给 Kimi 修一条同样的路。然后 Claude、Kimi、Codex 和我一起把它搭了出来。给模型协作用的工具，是靠模型协作搭出来的（这层递归，我进行到一半才意识到）。

[cc-fleet](https://github.com/ethanhq/cc-fleet) 走得更远。它把每个第三方工作者都跑成一个真正的 Claude Code 进程，只是把模型后端换掉，于是另一个模型家族可以坐进 Claude Code 本来就有的那些协调形态里：一次性的子智能体，一直活着、互相发消息的长期团队，按脚本步骤传递产物的多阶段工作流。而且座次表不是固定的：任何会说 Anthropic 或 OpenAI 兼容 API 的模型，都可以入席。

每多一家服务商，你的材料就多一个可能去的地方。审稿中的手稿、参与者数据、田野笔记、一切需要保密的东西——模型选择要从“什么东西根本不许离开你的机器”开始，然后才轮到哪家模型读得最好。

[OpenCode](https://opencode.ai/) 也值得知道，但主要出于另一个理由：它在你换掉底下的模型时把界面端稳，这让我最接近一次受控检验：所谓“模型差异”，到底出在模型，还是出在包着它的那个 harness。只是最接近，算不上干净——OpenCode 自己就会给每个模型家族挑不同的系统提示词和工具调用适配器，服务商的 API 在底层也仍然各不相同。[Carrel](https://github.com/linxule/carrel)，我在 [#4](https://www.threadcounts.org/p/research-with-ai-4-the-prompt-is) 里写过，坐在比这些都更早的一层，搭的是研究环境本身，信任和敏感度的边界也包括在内。感兴趣的话，我这套工具栈的完整地图在 [research-memex.org](https://research-memex.org/) 保持更新。

这一切之下还压着一个问题，实用的修补碰不到它：如果一家供应商同时提供模型、智能体、记忆，而且越来越多地提供评判工作的标准，那我的研究实践，有多少正在悄悄沉降成那家供应商的观看方式？我没有干净的答案。模型多样性消除不了依赖，只是把它摊到更多张账单上。但我知道在一个模型家族里待太久会发生什么：它的判断开始感觉像问题本身的形状。另一个模型，把边缘重新放回来。

该请另一位模型入席了。
